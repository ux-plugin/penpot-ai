00 · Orientation

How to read this

There is exactly one thing every part of the system touches: the document blueprint. Get its shape agreed early and the rest of the work stops needing to talk to itself.

The structure below follows that logic. §1 is the whole system on one page. §2 is the spine you lock first. §3 is how five streams then run in parallel. §4 names the interfaces that keep them from colliding and §5 specs each one. §6 is how a design becomes running preview code. §7 flags the decisions still open, and §8 defines the vocabulary.

One design rule underneath all of it: authoring tools are editors of the blueprint; the runtime is its interpreter; the renderer and emitter are its readers. Nothing bypasses the blueprint.

01 · The whole thing

System at a glance

Same picture, drawn the way you'll actually use it. Inside the preview layer, the Doc — the blueprint, holding its 2D, 3D, UI and interaction content — drives two things: the engine that plays vector / 3D / state-machine content, and the emitted UI code. The two talk (UI code hosts engine surfaces; the engine drives UI signals). The whole thing is then handed off into your own app, where the native components are yours to keep and the engine ships as a runtime.

Doc / blueprint Engine — vector · 3D · state machine UI code — native

Animation is not a fifth surface. It is described inside 2D, 3D and UI components — each keys its own properties and state machines — and all three feed the one animation IR (§5.3), played by the one engine. The blueprint is the only thing every box touches: freeze its shape early and the tracks stop needing each other.

02 · Lock this first

The spine — what everyone must agree on

Keep this layer small and stable. It is the coordination surface: the moment it is locked, the tracks fan out and stop depending on each other. Four parts.

  • Document blueprint — the persisted file: pages, boards, the shape tree, and everything below. The one format read & written by every track.
  • Named-cell store — one document-wide namespace of named cells. A cell is state (a stored value; a parameter when an element owns it) or derived (computed); shared state lives in stores owned by no element. Occurrences are interaction triggers, not cells. Wiring is derived from the names, not hand-plumbed.
  • Unified animation IR — one time/state model (a superset of Lottie / Rive / interaction semantics) that 2D motion, 3D, and transitions all target. Own the format; transcode other formats into it.
  • Reactive runtime — a reactive signal graph over state & derived cells is the execution substrate. Animation sampling and interactions both compile down to it, so a single blending sampler resolves every driver.

Why these four and nothing more: each is high-agreement and cheap to settle, yet every downstream stream needs it. Anything that can be decided inside a single track does not belong on the spine.

03 · The plan

How the work parallelizes

Serial where agreement is cheap; parallel where it is expensive. Lock the spine once (Phase 0), then five streams run side-by-side against frozen contracts and fixtures — no cross-blocking until integration.

The emitter sits in Phase 1 on purpose: it depends only on the frozen schema plus fixtures, so it can start immediately — long before any authoring track is finished. That is the payoff of freezing the blueprint first.

05 · Interfaces

Contract specifications

First-pass surface for each contract — the shapes to freeze in Phase 0. Representative, not exhaustive. Everything is addressed by a stable id, so the five streams reference the same entities without sharing code.

5.1 · Blueprint schema

data · the file

Not functions — a shape. The one document every stream reads or writes; all cross-references are by id.

// The persisted document — the single source of truth.
Document {
  id: Id
  pages: Page[]
  cells: CellStore          // §5.2 · document-wide namespace
  tokens: TokenSet          // design tokens / styles
  schemaVersion: int
}

Page {
  id: Id
  root: Shape               // board / shape tree
  motion?: PageMotion        // §5.3 · persisted as page.motion
  scene3d?: Scene3D          // optional 3D document
}

Shape {
  id: Id
  type: 'frame' | 'rect' | 'path' | 'text' | 'instance' | 'slot' | ...
  transform, geometry, fills, strokes, effects
  children?: Shape[]
  ports?: CellRef[]           // exposes state into the cell store
  interactions?: Interaction[]  // ECA sugar → signal graph
}

Invariants: ids are stable for a shape's lifetime · schema is additive/versioned (pre-production, so pick the cleanest shape) · nothing back-references except by id.

5.2 · Named-cell API

reactive · the wiring

One document-wide namespace of named reactive values. When you drop an element on the canvas, it exposes some of its values as named cells — a checkbox's checked, a slider's value. Everything else — interactions, animation inputs, other elements — binds to those names rather than reaching inside the element, which is why wiring is derived, not hand-plumbed.

A cell is one of just two kinds (triggers aren't cells — they live in the interactions model, defined with their producer node):

  • state — a stored, writable value. Called a parameter when it is an element's own (button.label, toggle.on).
  • derived — a read-only value computed from other cells, recomputed when they change (cart.total = sum(items)).

Every cell has an owner, and the owner sets its lifetime. Element-local parameters are owned by their element and deleted with it. Shared state is owned by a named store — it belongs to no UI element, is read and written by many, and outlives any one of them; it goes away only when the store does.

Reaching state you don't own — two ways, both read and write:

  • From an ancestor (containment) — a node reads and writes state owned by an enclosing node (Card.expanded, App.theme). Already in scope because it's above you; no setup. Use it when the state naturally belongs to a parent.
  • From a store (by name) — reference a named store from anywhere in the tree. Use it when the state has no natural parent or is shared widely, so you never hunt for a common ancestor to hoist to.

Both appear in one in-scope picker. Every write is an explicit authored interaction (on press → App.theme = "dark"), never silent mutation — and derived stays read-only.

state / parameter derived store
state / parameter
A stored, writable value — toggle.on, cart.count. Always has a current value; writing it notifies watchers. Element-owned ones (parameters) are deleted with the element.
derived
A read-only value computed from other cells, recomputed when they change — cart.total = sum(items). You never write it.
shared state
State or derived owned by a store, not any element — read and written by multiple elements, referenced by name, independent of any element's lifetime.
Trigger
An interactions concept, not a cell — the momentary node occurrence (press, tick, load) that fires a rule; the "when" of when → condition → action. Defined with its producer node; may carry a payload. Nothing is stored.
// One namespace. Two cell kinds — state and derived.
type CellId = string
Cell = { id: CellId; kind: 'state' | 'derived'; owner: NodeId | StoreId }

// values — 'state' is a 'parameter' when the owner is an element
defineState(owner, id, init): CellId
derive(owner, id, deps[], compute): CellId
get<T>(id): T
set<T>(id, value)                // state only; derived is read-only
subscribe(id, fn): Unsub

// shared state lives in a named store, owned by no element
createStore(scope): StoreId      // scope = an app boundary (or root); referenced by name
Store.define(id, kind, init?)      // cells that outlive any element

Lifetime: deleting an element deletes its parameters (dangling references get flagged); a store's cells survive until the store is deleted. Open: how a component's parameters scope across its instances — each instance needs its own values under one declared name.

5.3 · Animation IR / sampler

time + state → deltas

Animation is described inside the 2D, 3D and UI-component surfaces — not a separate track — and all of it targets one IR, resolved by the single blending sampler. That shared IR is what lets one engine play motion authored in any surface.

// IR — the data motion authoring produces
Track   { target: CellRef | ShapeProp; keys: Keyframe[]; easing }
Clip    { tracks: Track[]; duration: Time }
Machine { states: State[]; transitions: Transition[] }
PageMotion { clips: Clip[]; machine?: Machine }

// Sampler — the one blending sampler. Pure & deterministic.
createSampler(m: PageMotion): Sampler
Sampler.sample(t: Time, s: MotionState): PropDelta[]
Sampler.blend(layers: PropDelta[][]): PropDelta[]
Sampler.channels(): ChannelDesc[]      // what it can drive

Invariant: sample is pure in (t, state) — the same sampler runs at edit-scrub and at runtime, and deltas are keyed by the same ids as the blueprint & cells. Open: blend priority when a timeline clip and a state-machine transition target the same channel.

Runtime model — Rive, generalized to 3D

The engine borrows Rive's runtime model as a reference — not a rulebook — and it is not an ECS: a retained object tree with id-keyed properties, a mixing animation system, and a dependency-ordered dirty update, behind a swappable renderer. Rive is deliberately not ECS either, which is why the shape fits a hierarchical, moderate-count scene. We take what fits and diverge where our needs do — 3D, and our named-cell data-binding. The core still maps almost 1:1 onto the contracts above:

Extends Rive in two places: a 3D applier writes deltas onto the scene graph (TRS · bones · materials), not only 2D paths; and hot channels can go columnar beyond Rive's per-object apply where the count warrants. Drive modes: 3D and interactive 2D tick each frame; declarative 2D compiles to native drivers (WAAPI · Reanimated) where the platform allows. Format: .riv transcodes straight into this model; Lottie is the interop format.

5.4 · Scene query

read-only · into the engine

The queries authoring makes back into whichever engine owns the geometry. Never draws — backend choice stays render-internal.

// Read-only queries into the engine that owns the geometry.
// NOT how to draw — Skia/Vello/three/Myth stay render-internal.
interface SceneQuery {

  // pick — geometry-accurate hit testing
  hitTest(p: ScreenPt, opts?): ShapeId | null
  hitTestArea(r: ScreenRect): ShapeId[]

  // measure — resolved geometry, not declared values
  bounds(id: ShapeId): Rect            // after layout + transform
  tightBounds(id: ShapeId): Rect       // ink bounds incl. effects
  textMetrics(id: ShapeId): TextBox

  // project — coordinate mapping, incl. 2D ↔ 3D
  screenToCanvas(p: ScreenPt): CanvasPt
  canvasToScreen(p: CanvasPt): ScreenPt
  project3D(id: ShapeId, p: Vec3): ScreenPt
  unproject3D(p: ScreenPt): Ray        // screen → scene ray
}

Note: may be async / worker-backed (this editor renders off the main thread), so treat returns as possibly-promised. Answers reflect the rendered result — effects and 3D projection included. Existence of this contract is the §7 retained-vs-immediate decision.

5.5 · Emit target

blueprint → what ships

Lower once, then emit per platform. Three distinct things ship — don't conflate them: the components (native code you own), the runtime library (generic engine — signal graph + sampler + the WebGL/WebGPU renderer for surfaces), and the document bindings (per-design glue that boots the runtime). Content takes two paths, by kind.

// blueprint → what ships. Two paths by content kind.
lower(doc: Document): LoweredIR             // shared, target-agnostic
emit(ir: LoweredIR, t: EmitTarget): Project  // source + deps + assets

interface EmitTarget {                 // 'react-dom' | 'react-native'
  emitComponent(node): CodeUnit        // UI + interactions → native (div / RN)
  emitSurface(node): EngineMount        // vector-2D / 3D → engine-hosted surface
  emitBindings(cells, motion): CodeUnit  // per-doc glue: cells + sampler wiring
  emitAsset(asset): AssetRef           // images · fonts · glTF · .riv → project
}

Render split (decided): UI & interactions emit as native code (div / RN + signals); vector animations & 3D ship with the engine that renders them — they can't exist without it. The engine runs on WebGL + WebGPU. emitRuntime was a misnomer: it emits the bindings that boot the runtime lib, not the lib itself.

Decided: targets are div (web) + React Native; expressions stay untyped so the foundation is untouched. Open: ship the runtime lib as a tiny linked dependency, or inline it into the emitted project.

5.6 · Interactions (ECA)

trigger · condition · action

An interaction is a rule attached to a producer node: when a trigger fires, if a condition over state holds, run an ordered list of actions. That is the whole authoring act — "this trigger changes that cell." Everything outward (props, callbacks, server writes) is derived at lowering, never authored.

Interaction = {
  on: Trigger          // a node occurrence — press · hover · load · timer · swipe · animEnd …
  when?: Expr          // condition over state / derived (untyped); default true
  do: Action[]         // ordered
}

Trigger = { node: NodeId; kind: TriggerKind; payload? }   // lives on its producer node

// One data verb: write a cell. Subsystems expose their controls AS cells.
Action =
  | SetState { target: CellRef; value: Expr }
        // target = app state · a store · an ancestor
        //        · an animation input / playback cell   → this IS "animate"
        //        · the nav state / stack                → this IS "navigate" (lowers to the router)
        // sugar: toggle · adjust ± · add/remove/clear · reset
  | Emit     { trigger: TriggerRef; payload? }    // deliver an occurrence — chain a rule (or the rare bus)
  | Effect   { kind: 'toast' | 'haptic' | 'clipboard' | 'share' | 'media' | … }  // platform side-effect, no cell

// modifiers: delay(after) · per-action guard(if)
// NOT actions (derived): server mutation/fetch ← store-backed writes · A/B arm ← run-mode picker

One data verb. "Animate" and "navigate" aren't separate primitives — they're SetState aimed at cells the animation runtime and the router already own; the authoring UI just offers them as labeled shortcuts. Only Emit (an occurrence) and Effect (a platform call) fall outside SetState.

Outward effects are derived, not authored: the designer never says "call the server." Writing a store-backed cell lowers to a mutation / POST / callback as the target needs; a plain state write stays local. Expressions stay untyped so the foundation is untouched.

Lowering: an interaction becomes a guarded handler on its node — state writes flow through the reactive graph, navigation through the router, animation through input writes; store-backed writes add the mutation/callback. Attaches to any producer node — a visual element, or a non-visual one (timer · page/lifecycle · data source).

5.7 · Document Command API

one write path · propose · authorize

Every change to the blueprint — a human gesture, the AI, a plugin, an importer — is a typed command applied through this one API. Nothing mutates the document any other way. That single seam is why undo, proposals, permissions and AI all fall out of the same machinery instead of each needing its own path.

gated — review & authorize 
Command = { op: OpKind; target: Ref; args }   // setParam · createNode · wire · addInteraction · reparent …
Ref     = NodeId | CellId | StoreId

// external actors submit a Proposal — never a direct apply
Proposal = { by: Actor; steps: Step[] }
Step     = { ops: Command[]; why: string; focus: Ref[] }   // a human-legible chunk = one walkthrough step

// review → apply
preview(Proposal): ShadowDoc      // apply to a shadow copy; render / run, real doc untouched
accept(Proposal | Step)           // ops become journal entries (undoable)
reject(Proposal | Step)

// authorization — checked at the boundary, before validate + apply
authorize(actor, op, target): 'allow' | 'propose' | 'deny'

Suggest-vs-write is just authorization. The author is allow on their own doc (auto-apply); AI and plugins are propose (staged) — or allow inside a delegated subtree, deny on anything locked. Rights inherit down the tree; an explicit override on a shape (lock / another owner) wins over what its parent grants.

Structural ops authorize their whole written set. reparent(C, A→B) writes {C, A, B}; delete(A) writes A + its subtree. The decision is the strictest across those targets (deny > propose > allow), applied atomically — never half-moved. So a locked child can't be moved by the parent's owner, and you can't inject a shape into a container you don't own. Prefer downgrading a blocked structural op to propose (routed to the owner) over a hard deny.

A proposal is a script, so it renders as a walkthrough. Because steps are ordered, semantic and targeted, review has three views of the same data: a diff, in-place highlights, or a guided walkthrough — fly to each step's focus (scene query, §5.4), show its why, render before → after on the shadow doc, and run the resulting interaction/animation in the sandbox (same reactive graph). Accept per step. This is the review UX that makes suggest-mode usable.

Author-time only. This governs who may edit the design. Runtime permissions inside the emitted app are a separate layer, evaluated at a different time.

06 · Design → code

From blueprint to running preview

Preview mode is not a simulation of your design — it is real generated code. The blueprint is lowered, emitted to React DOM / React Native, and run. Because the editor runtime and the emitted runtime are the same reactive graph, what you preview is what ships.

The handoff — two paths into your app

Handoff is assisted: you emit into an existing codebase, not a sealed export. Content splits by kind. UI & interactions ship as native code you own — div / RN + signals. Vector animations & 3D ship with the engine: they need a renderer to exist at all, so they travel as engine-hosted surfaces plus the runtime that draws them. The engine runs on WebGL and WebGPU.

Blueprint Native path Engine path

Preview equals ship, precisely: the semantics — signal graph + sampler — are identical on both paths. Native surfaces are re-rendered by the platform (any fidelity risk lives here); engine surfaces are drawn by the same engine as the editor, so they are pixel-identical.

07 · Still to decide

Open questions

Two decisions are deliberately unresolved here — they change the shape of the spine, so settle them before Phase 1 fans out.

Decision · IR scope

Are cross-domain 2D↔3D interactions first-class in the IR?

This doc parks them in Phase 2, since 2D and 3D are the one place the tracks genuinely couple. If they need to be authored from day one, the animation IR must model them up front — a spine change, not an integration task.

Decision · editor mode

Retained or immediate — does Scene query exist?

If authoring only ever mutates the blueprint and the renderer redraws, there is no Scene query contract — the schema stands alone. If authoring drives the canvas imperatively (live scrub, overlays, worker-side picking, as today), the §5.4 surface must be frozen. This editor leans immediate, so the doc keeps it.

08 · Vocabulary

Glossary

Blueprint
The persisted document — pages, shape tree, cells, motion. The single source of truth every part reads or writes.
Named-cell store
One document-wide namespace of named cells — state (parameter when element-owned) and derived. Shared state lives in stores; occurrences are interaction triggers, not cells.
Store / shared state
A named reactive environment owned by no element, referenced by name — read & written by multiple elements, and outliving any of them.
Reactive signal graph
The reactive execution substrate over state and derived cells. Both animation and interactions compile to it, so one sampler resolves every driver.
Animation IR
The unified time/state model — a superset of Lottie / Rive / interaction semantics — that 2D, 3D, and transitions all target.
ECA
Event-condition-action — an interaction rule: on a node's occurrence (the trigger), if a condition over state holds, then act. Lowers to the signal graph.
Command / op
The atomic unit of change to the blueprint (setParam, reparent, wire…). The single write path; every actor — human, AI, plugin — produces these. Journal entries are commands.
Proposal
A staged change from an external actor — ordered steps of commands + a rationale + focus targets. Previewed on a shadow doc, reviewed (diff / highlight / walkthrough), then accepted or rejected.
Authorization
Per-target policy at the write boundary — allow | propose | deny, inherited down the tree. Subsumes suggest-vs-write, locking, ownership and AI/plugin scoping.
Sampler
Given a time and state, produces transform & property deltas. One blending sampler serves every animated driver.
Lowering
The pass that turns the high-level blueprint into the intermediate form the emitter consumes.
Emitter
Reads the blueprint and generates real React DOM / React Native code for the preview.
